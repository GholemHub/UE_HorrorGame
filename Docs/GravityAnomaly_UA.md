# Гравітаційна аномалія — чинний контракт

`ARoom::GravityAnomaly` працює лише на сервері та лише коли кімната проклята (`SetCursed(true)`). Участь беруть доступні для підбирання предмети з Actor Tag `GravityAnomaly`, які перебувають усередині `RoomVolume`. Вдале кидання запускає змінену гравітацію одразу; періодичний таймер може запустити падіння раніше нерухомого предмета або зачепити предмет, що вже падає. Предмет, який лежить на підлозі, таймер повторно не запускає. `bEnabled=true` без проклятого стану кімнати недостатньо.

Сервер один раз на початку падіння вибирає повільний або швидкий профіль (`SlowEventChance`), а потім прискорення з відповідного діапазону. За замовчуванням це **8,5** або **10,5 м/с²**; звичайна земна норма близька до **9,81 м/с²**. Налаштовувані `MinSlowGravity`/`MaxSlowGravity` та `MinFastGravity`/`MaxFastGravity` завжди обмежуються загальними межами 8,5–10,5. Під час активного падіння Chaos зберігає звичайну гравітацію, колізії та швидкість предмета; компонент кожен `PrePhysics` кадр додає тільки різницю прискорень через `AddForce(..., bAccelChange=true)`. Немає завмирання, обнулення швидкості, бокового чи вертикального імпульсу. На приземленні або при pickup/виході з кімнати/скасуванні прокляття додатковий вплив припиняється, а поточний імпульс руху не стирається.

Рідкісний хорор-варіант вмикають `bEnableUnseenDrop` і `UnseenDropChance` (типово 5% повільних падінь). Якщо хоча б один гравець своєї часової лінії бачить повільне падіння щонайменше 0,15 с, а потім предмет перестає бути видимим, сервер змінює прискорення до **10,5 м/с²** без імпульсу. На реальному зіткненні з підлогою надсилається одноразовий `MulticastUnseenImpact` лише відповідним слухачам timeline. `UnseenImpactSound` за замовчуванням використовує наявний `/Game/_Alex/Sound/DropSound`; для виразнішого гуркоту призначте окремий звук на компоненті `GravityAnomaly` у `BP_Rooms`. Якщо це поле очистити, використовується `DropSound` самого предмета, коли він заданий. Це навмисний виняток зі стабільної вибірки для вимірювання; для чистого експерименту поставте `bEnableUnseenDrop=false`.

`StrongEventChance` і `StrongEventObjectCount` тепер визначають лише рідкісне групове падіння кількох предметів, а не силу імпульсу. `ActiveItems` реплікується як поточний список для late join; `OnActivityChanged` відновлює/зупиняє локальний loop, `OnPropPhaseChanged` повідомляє короткий початок/завершення. У C++/BP слід не відтворювати старий one-shot із snapshot. `GetActiveGravityForItem` повертає вибране прискорення на сервері для діагностики; 0 означає, що предмет не бере участі. `bDebug=true` пише вибране значення й хорор-перехід у серверний лог. Поточний мережевий протокол — 14, тому старі та нові білди не повинні входити в одну сесію.

## Ручний сценарій

1. Запустіть listen host і окремий remote client. На конкретній тестовій кімнаті увімкніть `SetCursed(true)`, `bEnabled=true`, `bReactToItemDrop=true`, `EventChance=1`, `bDebug=true`. Для стабільних вимірів вимкніть `bEnableUnseenDrop`. Перевірте Actor Tag `GravityAnomaly` на `BP_Item2` або іншому предметі, який можна підняти. Не зберігайте тестові значення в gameplay-мапі без потреби.
2. Киньте предмет із достатньої висоти кілька разів від host та remote. Він має падати без паузи й зміни напрямку вбік. Серверний лог показує 8,5 або 10,5 м/с². Для точнішого вимірювання зафіксуйте висоту центру предмета `z0, z1, z2` через однаковий інтервал `Δt` до зіткнення; оцінка `g ≈ (2z1 − z0 − z2)/Δt²`, якщо висоти в метрах. Кидок із руки може мати початкову швидкість, але вона зникає з цієї різницевої формули. Короткий проліт дає шумний результат, тому використайте кілька відліків і усереднення.
3. Після падіння предмет не має самостійно «оживати» від таймера. Підніміть і киньте його знову: обирається новий стабільний профіль. Вимкнення прокляття або pickup під час падіння має зняти ефект без телепорту, зупинки чи бокового поштовху. Поза проклятою кімнатою падіння звичайне.
4. Для хорор-варіанта тимчасово задайте `SlowEventChance=1`, `UnseenDropChance=1`, `bEnableUnseenDrop=true`. Дивіться на повільно падаючий предмет хоча б 0,15 с, потім відверніться. У серверному логові має з’явитися перехід до 10,5 м/с²; при контакті з підлогою відповідний гравець чує удар. Перевірте, що через стіну або з іншого timeline предмет не вважається побаченим, а late join не повторює історичний звук. Значення 10,5 м/с² лише приблизно на 7% вище за норму, тож «раптовість» тут переважно створюють момент за спиною та звук, а не фізично надшвидке падіння.
5. Повторіть із 100–200 мс latency та 1–2% packet loss. На host, remote, late join/reconnect, після смерті/travel перевірте позу предмета, відсутність дубльованого звуку, завершення loop і cleanup. Командлет не доводить фактичну чутність чи плавність реплікованої фізики.

## Перевірка

`Hrono.Rooms.GravityAnomaly` тестує opt-in, server drop `BP_Item2`, виміряне повільне прискорення, безперервну гравітацію, відсутність бокового імпульсу та cleanup. `Hrono.Rooms.GravityAnomalyLanding` перевіряє швидке падіння, завершення при контакті, відмову повторно запускати предмет на підлозі, повторний кидок і перехід повільного хорор-варіанта після відведення погляду. Ручний мережевий/аудіотест вище залишається критерієм готовності для гри.

Перевірка 2026-10-03: повна збірка `HronoEditor` успішна; обидва фокусні тести гравітації пройшли. `Scripts/run_regressions.py` завершив шість перевірок; asset-contract аудит не знайшов нових відсутніх шляхів (24 відомі legacy audio paths лишаються відкритим боргом); read-only перевірка `DemoMap1` знайшла 0 проблем. У повному наборі `Hrono.` пройшли 17 із 19 тестів; окремо впали `Hrono.AI.MannequinContract` (перекриття видимості з Past timeline) і `Hrono.Items.PickupAssetsAndPlacement` (осі `BP_Monocle`). Повний мережевий та аудіо сценарій з двома процесами ще треба виконати вручну перед висновком про поведінку в грі.
