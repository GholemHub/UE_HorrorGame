# N02/N05 — серверна перевірка взаємодій

Дата: 2026-09-27. Робота після N01 і N03/N04. Blueprint assets та карти не змінювалися.

## Статус

**N02/N05: серверні перевірки реалізовано.** Залишкову авторизацію timeline закрито наступним кроком: [N02/L02 — timeline і смерть](N02_L02_Timeline_Authority_UA.md). Нижче опис попереднього interaction/drag кроку; ручний multiplayer-прогін ще потрібний.

## Що змінилося

- `AHronoCharacter::CanInteractWithActorOnServer`: authority, дійсність actor/world, Past/Future персонажа, timeline предмета, доступна query collision, досяжність геометрії та відсутність перешкоди на відповідному timeline-каналі. Дистанція рахується від серверної камери до collision, а не до actor pivot. Для complex-only mesh використовується найближча точка bounds. Функція не перевіряє напрямок погляду; це reach/line-of-sight policy.
- Pickup та environment interaction використовують цю перевірку. Локальний шлях хоста для environment також проходить той самий обробник.
- Старі й нові door/shelf RPC перевіряють конкретну авторську панель, ручний режим, ключовий/trigger lock, barricade, timeline, reach і видимість. Для продовження drag залишено запас 200 см до `InteractTraceDistance`; pickup/E/unlock використовують сам `InteractTraceDistance` (типово 500 см).
- Сервер приймає лише yaw у межах налаштувань відповідного `UDrag_Component`. Pitch/roll залишаються серверними. Shelf/cupboard використовують наявний clamp осі та довжини. Невідома панель, NaN/Infinity та неправильний тип панелі відхиляються.
- Host drag більше не змінює transform до перевірки. Клієнт зберігає локальне передбачення. CupBoardDrag передає назву рухомої панелі, як і решта шляхів; legacy RPC залишається сумісним і проходить ті самі правила.
- Ключ споживається лише якщо це справді поточний предмет у руці, його gameplay owner і network owner — цей персонаж, а двері доступні та не заблоковані trigger/barricade.
- RPC руни зберігає стару сигнатуру для сумісності, але ігнорує клієнтські `RequiredRuneId`, `SlotWorldTransform`, `RequiredRuneCount`. Приймаються реальна `ARunePentagram` і відомий відповідний слот; правила, transform, три руни та прогрес визначає серверна пентаграма. Перевіряються рука, обидва owner, held-state, timeline та доступність пентаграми. Звичайний E використовує той самий coordinator.
- Серверний `PlaceRuneInPentagram` залишається довіреним API для авторської логіки; мережевий RPC не може ним обійти coordinator.
- На момент interaction/drag кроку Timeline API лише перевіряв enum. У наступному кроці client-selected transitions повністю відхиляються; актуальний опис у [N02/L02](N02_L02_Timeline_Authority_UA.md).

## Що ще відкрите

1. Авторизацію timeline з цього пункту **виправлено наступною зміною**, включно з міграцією Blueprint смерті й усуненням повторного переходу пентаграми. [Поточний статус](N02_L02_Timeline_Authority_UA.md).
2. Drag session ownership, rate limits, final commit та примусова корекція клієнтського передбачення при відхиленні — окрема робота N06. Поточний сервер перевіряє кожен update, але не видає ексклюзивну сесію одному гравцеві й не обмежує швидкість руху всередині дозволеного діапазону.
3. Native automation викликає RPC-обробники в ізольованому authority world. Вона не доводить доставку пакетів, гладкість руху, відсутність візуальних відкатів або правильність звуку на віддаленому клієнті.

## Ручний сценарій — host + client

Запустити PIE з двома гравцями, Net Mode **Play As Listen Server**, бажано окремими процесами. Повторити дії спочатку клієнтом, потім хостом; другу машину залишити спостерігати. Пройти обидва timelines, потім повторити основні дії із затримкою мережі 100–150 мс.

| Крок | Дія | Очікування |
| --- | --- | --- |
| 1 | Підняти предмет, передати, викинути, відійти попереднім власником, підняти другим гравцем | Рівно одна рука володіє предметом, drop і повторний pickup працюють |
| 2 | Спробувати взяти предмет за стіною або в іншому timeline | Взаємодії немає; звичайний E сам по собі не доводить захист RPC — його обходи перевіряє automation |
| 3 | Відкрити звичайні двері; окремо перевірити обидві дверці шафи | Рухається потрібна панель у своїх межах; інша панель не змінюється |
| 4 | Потягнути кожну з трьох шухляд і cupboard | Власна вісь, межі й незалежні положення на обох машинах |
| 5 | Спробувати manual/E на дверях без ключа, з неправильним ключем, із правильним ключем | Лише правильний ключ відкриває замок і споживається один раз |
| 6 | Увімкнути trigger lock / залишити barricade; повторити з правильним ключем | Рух і споживання ключа блокуються; після зняття перешкоди доступ відновлюється |
| 7 | Почати drag, відійти понад дозволену дистанцію або зайти за стіну | Сервер перестає застосовувати updates; спостерігач не бачить продовження руху. Локальне передбачення/відкат оцінити окремо для N06 |
| 8 | Перевірити автоматичний режим E на дверях і шухлядах | Відкривання/закривання та правильна панель збережені |
| 9 | Послідовно вставити три правильні руни через E; спробувати неправильну/зайнятий слот | Невірна руна лишається в руці; правильна займає серверний слот; прогрес 1→2→3; третя завершує ритуал |
| 10 | Померти обома ролями та завершити ритуал після смерті | Стара послідовність смерті й timeline працює; це обов'язковий baseline після міграції N02/L02 |
| 11 | Підключити нового клієнта після placement та відкривання панелей | Узгоджені slot, owner та панелі; немає повторного pickup установленої руни |

Наявні звукові проблеми аудиту ця зміна не закриває. Під час кроків 3–9 записати, чи initiator/observer чують одну очікувану подію; native run використовує `-nosound`.

Запуск native automation у Developer Tools → Session Frontend → Automation: фільтр `Hrono.Items`, вибрати всі п'ять тестів (із новим TimelineAuthority) й Run. Перевіряти статус кожного тесту, а не тільки exit code процесу.
