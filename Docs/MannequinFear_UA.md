# Манекен: страх перед Бабаєм

## Налаштування анімації

На поставленому `BP_MannequinDemon` або в його Class Defaults відкрийте **Mannequin → Fear**:

- `Fear Animation`: Animation Sequence з переляком і присіданням на місці, на скелеті поточного skeletal mesh. Після завершення кліпу утримується останній кадр.
- `Fear Play Rate`: бажана швидкість, типово 1. Для довгого кліпу C++ підвищує її так, щоб вступ завершився не пізніше ніж через 5 с. Останній кадр кліпу має бути позою страху навприсядки, без вставання наприкінці. Окремий loop більше не потрібен і поле вилучено (у перевірених defaults воно було порожнім).

На момент перевірки поставлений Blueprint — `/Game/_Alex/AI/Mannequin/BP_MannequinDemon`, mesh — `SKM_KillerDollBase`, AnimBP — `KillerDoll_ABP`. Старий шлях `/Game/_Alex/AI/BP_MannequinDemon` перенаправляє до актуального asset. Самі анімації не призначалися й assets не зберігалися в цьому завданні. Анімацію потрібно ретаргетувати на скелет mesh, якщо скелети різні.

**Виявлена несумісність поточних assets:** `/Game/_Alex/AI/Mannequin/ь2/Terrified` (20 с), retargeted Idle та Walk використовують `SKM_KillerDollBase_Manny_IdleVerified_Skeleton`, а поставлений body — оригінальний `/Game/FreeKillerDoll/Asset/Meshes/SKM_KillerDollBase`. Призначення такого `Terrified` без узгодження скелета не запускає native fear sampling. Поточний locomotion ABP на оригінальному body також викликає `lowerarm_correctiveRoot_l contains NaN`. C++ не змінює авторський body чи retarget assets автоматично. Для тесту використано однойменний `IdleVerified` mesh із відповідним скелетом лише в пам'яті тимчасових акторів/процесів.

Нові графи, Montage Slot чи AnimNotify для запуску не потрібні. C++ тимчасово відтворює позу sequence у стані `SubmissiveToBabai`, потім відновлює попередній Animation Blueprint. Це стан поведінки з керованим часом анімації; наявна state machine локомоції не перебудовується. Notifies цих кліпів не виконуються: sampling пози не повинен повторювати історичні звуки чи gameplay-події.

## Серверний контракт

Після підтвердження справжнього hunt Director переходить в `Anticipation`. Через **5 секунд ігрового серверного часу** запускається `Manifestation` і штатний спавн Бабая. Затримка діє й для `SkipWarning`; хибне звичайне попередження не запускає страх. `EndHunt`, скидання сценарію та `EndPlay` скасовують таймер. Заборона спавну під час ритуалу лишається чинною.

Манекен переходить у `SubmissiveToBabai`, припиняє path following і вимикає movement. Пошук предметів, переслідування, атака та зміна Mood не виконуються. Таймер пропозиції предмета призупинено на час страху; предмет залишається у руці. `ForceTarget` і QA-зміна Mood не можуть скасувати страх. Без призначеної анімації gameplay-блокування однаково працює.

Погляд будь-якого гравця, напряму або через монокль, **не призупиняє** анімацію страху й не затримує вихід. Правило завмирання під поглядом залишається для звичайної поведінки манекена. Кліп починається одразу й досягає кінцевої пози за максимум 5 с; коротший кліп утримує її раніше. При `Manifestation` сервер додатково фіксує `bHoldingPose`, зокрема для активації манекена посеред hunt. Фінальна поза утримується протягом усього страху.

Капсула та skeletal mesh мають `NoCollision` протягом страху на сервері й клієнтах: через манекена можна пройти. Після виходу відновлюються штатна колізія активного стану та збережений authored collision mode mesh з чинними timeline-фільтрами. `OnRep_State` і `OnRep_FearPlayback` обидва застосовують фізичний стан, тому порядок отримання snapshot не лишає колізію увімкненою.
`FearPlayback` реплікує активність, ознаку утримання фінальної пози, clock (без пауз під поглядом), накопичений час, серверну часову позначку, номер запуску та зафіксовані location/rotation. Останні потрібні також клієнтам із уже вимкненим CharacterMovement, щоб не лишатися зі старою позицією. Клієнти семплюють поточний кадр; late join/relevancy відновлює актуальну позицію без повторного вступу чи notifies. Root motion не переміщує актора. Реплікований `State` зберігає штатний контракт snapshot/one-shot.

Страх триває через `Anticipation`, `Manifestation`, `Searching`, `Chasing`, `Ending`. Після небезпеки діє наявний `Babai Recovery Delay` (у поточному BP 8 с; можна виставити 0). Після recovery delay вихід відбувається незалежно від погляду; Animation Blueprint і колізія відновлюються. Деактивація/знищення очищає стан; знищення Director не залишає вічне блокування. Сумісність мережевої сесії — protocol 23.

## Перевірка

`Scripts/inspect_mannequin_fear.py` читає активні pin connections, AnimBP, CDO та placed defaults без збереження карти. `Hrono.AI.MannequinFear` перевіряє затримку фактичного SpawnActor, незмінну позицію, безперервний вступ під поглядом, фінальну позу, колізію, другого спостерігача в одному timeline, відновлення snapshot і AnimBP, скасування відкладеного спавну й деактивацію. Результати запусків наведено нижче після завершення перевірок.

Ручний acceptance з остаточною анімацією: host + remote, прямий погляд/монокль/стіна, відведення й повторне наведення погляду посеред присідання, late join і reconnect під час утримання пози, 100–200 мс latency та 1–2% loss, смерть/перехід timeline, скасування hunt і travel. Перевірити, що обидва бачать однакову позу, capsule не рухається, обидва гравці проходять крізь тіло під час страху, колізія повертається після виходу, предмет/маска слідують кісткам, фінальна поза придатна для утримання. Headless-тест не підтверджує якість анімаційного переходу.

## Попередні результати 2026-10-08 (до скасування паузи під поглядом)

- Фінальна збірка `HronoEditor Win64 Development` успішна, включно з виправленням world-pose snapshot після першого мережевого прогону.
- Повний `Automation RunTests Hrono.` без `-nosound`: **24 Success / 2 Fail**. Новий `Hrono.AI.MannequinFear` пройшов, включно з pause/resume, actual spawn delay, нерухомою позицією, snapshot, скасуванням спавну й cleanup. Звіт: `Saved/Tests/Mannequin/Fear/FullAutomationFinal/index.json`.
- `MannequinContract` падає під час створення authored BP через наведений вище NaN у locomotion; `PickupAssetsAndPlacement` має три давні помилки осі монокля. Ці помилки не приховано та не виключено зі звіту.
- Усі сім скриптів `run_regressions.py` завершили власні перевірки успішно; під час читання карти engine додатково видає той самий NaN ensure. Тому це не чистий commandlet pass. Лог: `Saved/Tests/Mannequin/Fear/regressions_final.log`.
- Asset contracts: 0 required/new missing, **24 відомі legacy audio paths лишаються відкритим боргом**. Read-only map validation: 1044 актори, 0 contract issues; engine також повідомляє NaN ensure. Карта не зберігалася.
- `Scripts/test_mannequin_fear_network.ps1` + `Scripts/analyze_mannequin_fear_network.py`: **20/20 перевірок пройшли** на фінальному коді, listen host / remote / reconnect, `PktLag=100`, `PktLoss=2`. Виміряний інтервал Anticipation→Manifestation у логах — 5,03 с (таймер 5 с спрацьовує на наступному кадрі). На host і remote під поглядом зафіксовано той самий кадр 10,100 с; після відведення погляду час продовжився. Усі active snapshots мають одну світову позицію. Reconnect отримав актуальний час понад 43 с і фінальну позу 20-секундного тестового кліпу, без повторного вступу. Host cleanup скинув active fear. Машинний звіт: `Saved/Tests/Mannequin/Fear/Network/analysis.json`.
- Ручна візуальна перевірка з остаточно призначеною анімацією, монокль у двох процесах, смерть і travel ще потрібні. Автоматизований network probe не замінює цей acceptance.
